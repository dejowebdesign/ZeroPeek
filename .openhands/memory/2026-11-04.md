## Concurrent answer submission – bugfix (PR #28)
- Branch `fix/concurrent-answer-submission` from `origin/main` `202b143c` (PR #27 admin merged).
- **Root cause:** `engine.submitAnswer` was check-then-act with no mutual exclusion AND mutated the
  runtime *before* the write. Two overlapping answers both passed the `answeredQuestionId` guard,
  both added score/time/correctCount/distribution; the `@@unique([playerId, questionId])` index
  rejected the second insert but the runtime had already drifted, and the Prisma `P2002` surfaced as
  a generic **500** (`guard` maps non-AppError → "Unexpected error.") instead of the established 409.
- **Second race (the reachable one):** `engine.get()` built a fresh `RuntimeGame` on a cache miss, so
  concurrent cold requests each got their own object; last `games.set` won, others mutated an orphan.
  For a *warm* game Node's run-to-completion makes the guard+mutation atomic, which is why naive
  `Promise.all` tests pass on the old code — the real repro needs an evicted (cold) game.
- **Fix:** (1) commit both writes in one `prisma.$transaction`, mirror runtime only after it resolves;
  (2) map `P2002` → `conflict('You have already answered.')`; (3) `withAnswerLock('playerId:questionId')`
  async chain (`Map<string, Promise<void>>`, tail never rejects, key deleted when last task settles);
  (4) `get()` shares one in-flight load per game (`loading` map).
- **Prisma client is a `Proxy`:** `vi.spyOn(prisma, '$transaction').mockRestore()` leaves the property
  **undefined** (cleared, not restored). Must reassign the original explicitly in `finally`.
- Tests: 6 new in `engine.integration.test.ts` (9→15). Red on the unfixed engine: A (parallel
  duplicates on an evicted game), D (failed `$transaction`), F (concurrent cold `get`). Backend suite
  **154** (was 148); frontend 285; shared 89. Build/lint/typecheck/format clean; no migration.
- Report: `docs/reports/concurrent-answer-submission-fix.md`. `docs/phases.md` 6.5.1 → merged (PR #27).
- `docs/phases.md` has **no bugfix section** — the task said not to invent a phase, so only the stale
  6.5.1 row was corrected.

## Player reconnect state sync (PR #29, branch `fix/player-reconnect-state-sync`)
- Bug: a refreshed/reconnecting player always saw the lobby. Cause was twofold:
  `player:rejoin` ACK was `{ ok: true }` (joined rooms, returned no state) and
  `pages/player.ts` called `showWaiting()` unconditionally. State transitions
  (`game:question/reveal/board/ended`) are one-off events, so a socket arriving
  after them never saw them — there was no "replay current state to this socket".
- Fix: new shared `PlayerSync` contract (`phase`, public question, the player's OWN
  answer state, `board`/`podium`/`placement`). `player:rejoin` returns it; built by
  `engine.playerSync(game, playerId)` from existing public views + that player's
  `PlayerAnswer` row (never leaks `correctIndex` or others' answers). `engine.load`
  recovers `openedAt` from the persisted `question` `GameEvent` and the answered set
  from `PlayerAnswer`, then re-arms the timer or defers a reveal. Frontend
  `screenForSync` maps phase→screen; answered question renders inert.
- Pitfall: calling `this.reveal()` inline inside `load()` deadlocks — the runtime is
  not in `games` until `load` returns, so the reentrant `get()` awaits the load that
  is running it. Defer with `setTimeout(..., 0)`.
- **Pre-existing race found while testing (fixed on the same branch):** the
  fire-and-forget auto-reveal from `submitAnswer` (fired when the last player
  answers) could interleave with a host's `end`; `setPhase('reveal')` could land
  after `setPhase('end')`, leaving a finished game persisted as `reveal` with no
  `endedAt`. **Reproduced deterministically: 47/150 iterations wrong on `origin/main`.**
  This is what made `snapshot.integration.test.ts` "counts statistics" fail
  intermittently in CI (a game not in `end` isn't counted). Fix: per-game phase lock
  (`withPhaseLock`) around `start`/`next`/`reveal`/`board`/`end`, with `*Internal`
  bodies so a transition that triggers another doesn't re-enter the lock.
- Test recipe: `DATABASE_URL=postgresql://zeropeek:zeropeek@localhost:5432/zeropeek_test?schema=public`
  (prisma reads `DATABASE_URL`; the test helper also accepts `TEST_DATABASE_URL`).
  `npx vitest run --root packages/backend`; `fileParallelism:false` in
  `packages/backend/vitest.config.ts` (shared DB, each suite truncates).
- Repro pattern for that class of bug: loop the scenario ~60–150× and count the bad
  states; a single run usually passes, so a one-shot assertion is not a real guard.

## Phase 6.6.3 – host/player identity separation (analysis done, impl on branch, awaiting approval)
- Root cause confirmed: ONE cookie `zp_session` (`path=/`, HttpOnly) is read by every
  surface. Profile page boots via `GET /api/auth/me` → shows the signed-in ADMIN.
  `player:join` also did `resolveSession(...) → session?.user.id → engine.join(...)`,
  so a "guest" join from an admin's browser was attributed to the admin's account.
- Fix: two identity contexts. Host keeps `zp_session`; player gets
  `zp_player_session` (`PLAYER_COOKIE_NAME`, default `zp_player_session`). Session row
  gets `kind` ('host'|'player', default 'host' + index) via additive migration
  `20261110120000_phase_6_6_3_session_kind`. Guards: `requireAuth` (host, reads
  `request.auth`) vs `requirePlayerAuth` (player, reads `request.playerAuth`).
  `resolve()` rejects a session whose `kind` mismatches the requested context.
- New routes: `POST /api/player-auth/login` (role PLAYER only), `.../logout`, `GET
  .../me`. `GET/PUT /api/profile` now use the PLAYER guard. `player:join` resolves the
  PLAYER cookie only (never the host cookie). `/host` namespace unchanged.
- Frontend: profile page boots via `/api/player-auth/me`, has its own player sign-in
  form + Sign out; `auth.html` remains the host sign-in. Host-only browser → player
  sign-in mask (not the host identity).
- Tests: new `identity-separation.integration.test.ts` (22 tests, T01–T20). Full gate
  green: backend 271, frontend 357, shared 106; typecheck/lint/format/build OK.

## The design that matters

- **One background per round, decided at creation.** `engine.create` picks a random catalogue entry
  and immediately appends a `background` `GameEvent`. Joins, starts, question changes and renders
  never re-roll it — the binding Phase 5c rule (*"Standard Zufall einmalig je Runde"*).
- **The `random` sentinel is resolved server-side, once.** `resolveBackgroundChoice` turns
  `'random'` into a concrete id (`undefined` for a hand-made id). The client only ever sends the
  sentinel, so two devices can never roll two different images.
- **Unchanged value = no-op.** `setBackground` returns early when the resolved id equals the current
  one, so a double click or a repeated `random` cannot swap the image under a running show.
- **No migration.** The choice lives in the existing `GameEvent` log and `load()` restores the last
  valid `background` event. `engine.evict(gameId)` therefore exercises the real restart path.

## Two real bugs the new tests caught

1. **The `host:background` listener was never registered.** `attachHostHandlers` keeps an explicit
   `listeners` array — adding the handler to the `HostEventHandlers` *type* is not enough. The
   picker still worked through the command ACK, so only the *live broadcast* was dead. **Any new
   host event needs an entry in that array.**
2. **The picker vanished on a reconnect.** A reload arrives as `{ kind: 'sync' }`, not
   `{ kind: 'lobby' }`, so checking `lastRender.kind` hides the picker exactly when the host
   reloads. Match on `hostScreen(state)` instead.

Both are covered by `hostPage.test.ts`, which drives the real page in jsdom with a fake socket.

## Phase 6.11 adjustment — music for the whole running game

Owner changed the rule: the supplied track is the **round's bed**, not a question cue.
It starts with the first question and stops only at real game end.

**Server facts that made this easy (verified in `engine.ts`):**
- `enterLead()` is called **only** from `start()`; `next()` goes `board → question`
  directly and `advance()` never re-enters `lead`. So **a `lead` between questions does
  not exist today**. The rule still handles it in case one is introduced.
- `HostState` has **no question index** (`question` is null outside question/reveal/board),
  so "has the game begun?" cannot be read from a counter on the client.
- The answer is the phase ordering itself: `question`, `reveal` and `board` are only
  reachable **after** a question opened, so any of them proves the round is under way.
  `lead` is the only ambiguous one → **`lead` never starts the track, it only lets a
  running track continue**. `this.playing` is the latch; nothing local is guessed.

**Implementation:** `isStartPhase(phase)` = question|reveal|board (new export);
`isMusicPhase` now includes lead; `shouldPlay(phase, paused, running)` returns
`paused ? false : isStartPhase ? true : phase==='lead' && running`.
`sync()` early-returns when intent is unchanged, so `question→reveal→board→lead→question`
issues **zero** `play()`/`pause()` calls — one play per round, one pause at `end`.
`host.ts` and `tokens.css` needed **no** change (the page already passes the phase).

**Test hygiene worth remembering:** running a single frontend test file from the repo
root gives `document is not defined` — `packages/frontend/vitest.config.ts` sets
`environment: 'jsdom'` and only applies when run **from the package dir**
(`cd packages/frontend && npx vitest run src/<file>.test.ts`). This failure pre-exists on
`main`; it is not a regression.

**Negative control paid off:** reverting `shouldPlay` to `phase === 'question'` fails 6
tests including the real-page DOM test, which proves the new test actually bites.

## Phase 6.11.3 — Podium-Feuerwerk unsichtbar: Ursache und Rewrite

**Symptom:** Auf dem Server lief nur der **Ton** der Siegerehrung, visuell war nichts zu

## Phase 6.11.3 (Runde 2) — Feuerwerk auf Beamer-Größe: 4 % → 15–34 %

**Auftrag:** 4.07 % Peak waren für ein Showfinale zu klein. Zielkorridore: große

Alpha-Histogramm-Messung machen (>8 wash, >64 body, >128 hot, >200 core).

## Round background vs starfield harmonisation (Section 2 addendum)

**Root cause: the scrim, not the opacity, was hiding the image.**
`[data-round-background]::after` used `rgba(6,8,20, .72→.86)` — that is the
"opaque overlay" the brief forbids. Measured by correlating the rendered frame
with the source motif (card masked out):

| config | corr with source |
|---|---|
| 0.5 opacity + 0.72/0.86 scrim (old) | **0.142** |
| 0.38 opacity + scrim kept at 0.72/0.86 | **0.101** (worse than old!) |
| 0.38 opacity + 0.32/0.46 scrim (new) | **0.253** |

Lowering opacity *alone* makes it worse because the scrim is then a larger share
of what you see. Both layers had to move together.

**Contrast is carried by the card, not the scrim.** All show text lives inside
`.show__board.card`; its glass fill + 16px backdrop-filter give 17.7:1 on the
*brightest* supplied motif (`zeropeek_synthwave_megacity_detail.webp`, mean luma
53, p95 178). The `@supports not (backdrop-filter)` fallback is opaque
`--glass-fallback: #12121f`. So the scrim protects nothing the card doesn't.

**Starfield on the show surface is `.centered::before`, NOT `.starfield`.**
`.starfield` only exists on auth/join pages. `.centered::before` tiles 6
radial-gradients at z-index -1 and is the layer the "stars must stay visible"
requirement applies to on host/beamer.

**Measured star-opacity finding (counter-intuitive, worth remembering):**
over the photo, star visibility peaks early and then saturates.
- starO 0.15 → maxΔ **11/255** (invisible, field reads flat)
- starO 0.30 → maxΔ **24/255** (= same peak as 1.00)
- starO 1.00 → maxΔ 24/255

So dimming stars to 0.30 loses **nothing perceptible**, but 0.15 crosses into
invisible. The brief's lower bound (0.15) is the unsafe end, not the upper one.
Set `opacity: 0.3` with a comment; do not go below ~0.25.

**Final values** (`backdrop.css`): image `0.38` (phone `0.32`, reduced-transparency
`0.26`); scrim `radial .32` + `linear .32→.46`; `.centered::before` `0.3`.
Photo contribution to frame 2.84 → 6.16 (+117%); frame luma +10–14% at every
viewport 1920/1440/1024/430. Stars still measurably present (maxΔ 24–25).

Contract tests updated in `design-system.test.ts`: opacity band 0.25–0.45, every
scrim alpha ≤0.46, star opacity 0.25–0.35. A test pins values so they can't drift.

**Measurement recipe** (no PNG viewing): serve the two backdrop.css versions,
screenshot with headless chromium at a fixed window size, then in numpy mask the
card rect and compare `|frame - frame_without_image|` plus `corrcoef(frame,
source_motif)` downscaled to source size. `pip install pillow numpy` needed.

# Phase 6.14 – Host-Lobby: QR + Hintergrund-Karussell

## Warum der QR „fehlte"
`joinQr.ts` war **vollständig** (`joinUrl()`, `qrSvg()`, `renderJoinQr()`), wurde aber von
**keiner** Seite importiert. Kein Rendering-Bug, sondern fehlende Verdrahtung. Lehre: bei
„Feature ist weg" zuerst `grep -rn "<modul>" src/` — ein unbenutztes Modul sieht wie ein
gelöschtes aus.

## Umsetzung
- Join-Szene `pages/host.ts`: `.lobby__qr` + `renderJoinQr(host, pin)`.
- Karussell: `backgroundPicker()` + `paintCarousel()`. `paintCarousel()` schreibt nur
  Position/Labels neu, **baut die Buttons nicht neu** → Fokus bleibt beim Host.
- `shared/backgrounds.ts`: `BACKGROUND_CHOICES` (Random zuerst), `stepBackground()`
  (Wrap-around), `backgroundChoiceName()`, `pickRandomBackground(random, exclude)`
  (Random erneut drücken ist kein toter Klick).
- Engine persistiert die **Karussell-Position** im Event-Log, nicht nur das aufgelöste
  Bild; unbekannt/alt → Random. `backgroundChoice` reist in `sync` + beiden Broadcasts.
- Anzeigenamen gekürzt (nur Labels!). IDs/Dateinamen/Pfade unverändert, sonst brechen
  gespeicherte Spiele.

## Fallen
- **`tsx watch` stirbt hier** mit `EBADF: bad file descriptor, read`. Lösung:
  `npx tsx src/server.ts` ohne watch.
- Backend-Port kommt aus **`BACKEND_PORT`**, nicht `PORT`.
- Login per curl braucht CSRF: `GET /api/auth/me` → `csrfToken`, dann `x-csrf-token`.
- Test-PINs müssen im PIN-Alphabet liegen (`B` ist **nicht** enthalten) — `isValidPin`.
- Karussell-Klick „wirkte" wirkungslos: `browser_get_content` war verzögert,
  `browser_get_state` zeigte korrekt `2 / 11`. Bei DOM-Prüfung State statt Content lesen.

## Scannbarkeit wirklich geprüft
Modulmatrix bei 8× in `Uint8ClampedArray` gerendert und mit **`jsqr`** (fremder Decoder,
temporär in `/tmp`) zurückgelesen → `ENCODED === DECODED`, danach `/tmp` gelöscht. Das eigene
`qrcode-generator`-Modul zurückzulesen wäre ein Zirkelschluss.

## Bug A — Skip/End sent before the confirmation

- Root cause (empirically confirmed in jsdom, no screenshots): `hostButton()` already bound the
  command through the button's `onClick` — `el()` in `dom.ts` attaches with **`addEventListener`**.
  `controlsFor()` then set a **second** handler with `node.onclick = () => confirmDialog(...)`.
  Both listeners ran on one click: the command went out **immediately** *and* the dialog opened.
  Cancel could not undo the send. (This is why the "skip is neutralised" note in 6.5.3 was a lie in
  practice — the confirm dialog never actually gated the send.)
- Fix: `hostButton(label, action, { variant, confirm? })`. When `confirm` is set, opening the
  dialog is the button's **only** click action; the command is sent from `onConfirm`. `controlsFor`
  no longer overrides `onclick`. Invariant: **never bind a command via `onClick` and then add a
  second `node.onclick` on the same element** — use one handler that branches.
- Regression tests in `hostPage.test.ts`: dialog opens with **zero** sends, Cancel sends nothing,
  confirming sends exactly once (both Skip and End). Verified failing on the pre-fix code (2 fail).

## Bug B — "Next question" shown on the last leaderboard

- The board always rendered **Next question**, including the **last** board, where the next click
  ends the game. The client had no data to distinguish "more questions" from "last", so it could
  not be hidden. The earlier "Next button missing" report is the same confusion.
- Fix: engine derives `hasNext` (`currentIndex + 1 < quiz.questions.length`) and carries it on the
  `board` event and in `HostState`; `socket.ts` forwards it to `host:board`; `hostActions(phase,
  paused, type, hasNext)` omits `next` on the board when `hasNext` is false. Derived server-side, so
  a reload/reconnect on the board restores the same controls.
- Display only: `engine.next` still refuses any non-`board` phase.

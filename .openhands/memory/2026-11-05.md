## Regression analysis: host/player roles + answer-button layout (text-only, no code changed)
- **Owner directive (new, durable):** host = facilitator ONLY (no player identity, never
  answers); player = participant ONLY (answers one of ≤4 options, never controls the
  round); beamer = the existing **combined host view**, presentation only, NOT a separate
  surface/route. Clock position is explicitly OUT OF SCOPE (later design phase).
- **Verified: role separation is intact, server-enforced.** Clients are separate bundles
  (`index.html`→player.ts, `host.html`→host.ts) on separate namespaces (`/` vs `/host`,
  host namespace cookie-authenticated in `backend/src/socket.ts`). host.ts never emits
  `player:*`; player.ts never emits `host:*`. Backend: `submitAnswer` requires
  `socket.data.playerId`+`gameId` (set only by `player:join/rejoin`) → a host socket cannot
  answer; all `host:*` commands go through `assertHost` (owner or ADMIN). Host is never a
  `GamePlayer`. `host:answers` is sent to the host ROOM only. So there is **no client-side
  role swap**.
- **Root cause of the visible "role/beamer" defect (confirmed, reproducible):** PR #19
  (`cd05438`) added `.centered.show { justify-items: stretch; padding: … }` (tokens.css
  ~L1508). The section is a grid item of `<main>`; `justify-items` controls the *items
  inside* the section, not the section itself. Its `max-width: var(--show-measure)`
  (`min(94vw,1500px)`) collapses to content width (~1200px board) and the section stays
  left-anchored with only `main`'s 16px padding → the whole beamer board sits far left
  (1920px: board.left=16, L/R margin 16/704) instead of centred. The in-board
  `.show__options` grid is fine.
- **Pre-PR19 the beamer board was centred** (`.centered{display:grid;place-items:center}`,
  `.show{width:100%}`); PR #19 added `max-width` to `.show` without centring the section.
- **Verified fix (D, text-measured):** centre the section itself —
  `.centered.show { justify-items: center; margin-inline: auto }` → board.left = exact
  centre at 1920 (360), 2560 (680), 1366 (83). `justify-items:center` alone or
  `margin-inline:auto` alone are insufficient (need both).
- **Player answer buttons:** `questionView.questionInput` puts `.option` buttons into
  `.question__input`, which has **no CSS rule** → they are block-flow, one full-width
  button per row, stacked (player card is capped by `--content-max: 1180px`). Owner wants a
  **2×2 grid for ≤4 options**, responsive single column on narrow screens. `.show__options`
  already does exactly this but is host-only; `.question__input` needs the equivalent grid.
- **Note:** `MAX_ANSWER_OPTIONS = 6` (not 4) in `shared/src/constants.ts`; owner spec says
  max 4 answer buttons. Confirm the intended cap.
- Long-label stress: player at 390×844 overflows vertically (page scrolls, content not
  clipped) — a pre-existing mobile behaviour, not caused by PR #19.
- Text-only measurement recipe that worked: `npm run build -w @zeropeek/frontend`, then
  `npx esbuild <probe.ts> --bundle --alias:@zp-frontend=./packages/frontend/src` against the
  built `assets/ui-*.css`, serve `dist/`, and read `getBoundingClientRect` via
  `chromium --headless=new --dump-dom` (element rects + computed styles, NO screenshots).

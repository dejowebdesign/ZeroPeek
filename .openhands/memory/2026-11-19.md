## Gotcha: a stale local `main` ref

`git rev-parse main` still showed `84275c0` after the merge, because a server-side merge does
not move the local `main` ref. Always `git fetch origin main` (or `git ls-remote origin
refs/heads/main`) before claiming anything about the current state of `main`.

## Gotcha: reporting a status from a cached snapshot

The "`merged: false`" status that was reported while the merge was in flight did **not** come
from GitHub serving stale data. It came from reading a JSON file that had been fetched at
20:28:07, i.e. *before* the 20:31:46 merge. GitHub's API was correct throughout.

Lessons that actually hold:

- The owner can merge at any moment while a session is still polling. Re-query immediately
  before reporting a status; never report from a snapshot taken minutes earlier.
- Do not treat a cached JSON file as current across a possible state change. Re-fetch.
- When the PR endpoint and `/issues/<n>/timeline` disagree, the timeline (or
  `git ls-remote origin refs/heads/main`) settles it.
